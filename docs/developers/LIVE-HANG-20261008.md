# October 8 live crash hang

## Captured evidence

The non-responsive shared template process (PID 6852) was inspected before a new test run. The application remained CPU-active while its main thread was inside managed JIT code. A full dump, native thread stacks, registers, loop disassembly, logs, graphics settings and the `fdgxf` save were preserved under `artifacts/diagnostics/live-hang-20261008`. The debugger subsequently closed the hung application when a managed-symbol function call failed; the full dump had already completed. No diagnostic dump has been uploaded.

This run used seed 1403775798 and Random terrain selection 371325661, arriving at along 80,814,534,555.0796 m / across 71,203,081.1879123 m. The log ends during Aeris 4A impact/debris initialization, not a post-crash relocation. It includes wheel punch-through and multiple part explosions. The earlier dead-vessel relocation guard is therefore not a fix for this particular hang.

The stopped instruction is the repeated-addition loop in KSP's legacy `UtilMath.ClampRadians`. The dump contains angle -616,194,345,473.6643 radians; adding one revolution per iteration would take about 98 billion iterations. Its disassembly matches the inspected stock helper: subtract 2*pi while above its positive endpoint, then add 2*pi while negative. Read-only decoding of the dump's Mono JIT metadata resolves the stack as `Update -> OnUpdate -> UpdateTopData -> CalculateStartEndXferTimes -> TransferMath.AlignmentTime -> UtilMath.ClampRadians` (recorded in `resolved-stack.txt`). This establishes a CPU-bound stock transfer-planner stall, rather than a GPU draw wait or conic-solver update. Large interstellar orbit-radius ratios can produce enormous target phase angles in this planner; a finite angle is not necessarily cheap to wrap. No claim is made that the crash itself is required to trigger this stock planner path.

## Treatment

A Harmony prefix leaves ordinary `ClampRadians` calls alone and reduces large angles with remainder. Positive multiples retain the stock inclusive 2*pi endpoint; negative multiples produce zero. Infinity becomes NaN instead of entering a loop that can never finish. This exceptional-input guard applies to the stock helper regardless of caller because the helper has no vessel argument. It does not replace planetary gravity, change celestial body identities, or change ordinary patched-conic calculation.

New rotating-frame participants also publish their inertial bookkeeping orbit immediately on registration, before the next physics update. This separately reduces the opportunity for newly detached parts' stock modules to query an orbit built from surface-relative velocity. That bookkeeping improvement is not the evidence for the transfer-planner hang: the bounded angle helper directly treats the captured loop, including callers using large but valid interstellar orbits.

## Validation

Core tests include the captured angle, very large finite positive/negative values, positive/negative revolution endpoints, infinity and NaN (110,600 total checks passed). `LiveHang-replay.log` passed the patched stock helper's exact captured-angle/infinity checks, a normal-gravity wheels-deployed approach at the reported seed/coordinates, and continued through impact/debris/destruction for 1,811 frames. Dead-craft relocation refusal and all-biome asset binding also passed. A replay is an approximation of pilot input, not certification of every manual landing. `Desert-scatter.log` also calls the identified `TransferMath.AlignmentTime` with an interstellar-distance fixture; it returned a finite alignment result in 0.1384 ms. This verifies termination of the actual stock planner path; it does not make stock planetary transfer estimates physically accurate for a rotating habitat.

Dependencies and local development status are unchanged. No Git operation, release archive or publication is part of this investigation.

The normal development base DLL is installed after verification, with the smoke harness removed. The user's preserved graphics settings were restored. The local dump is approximately 10 GB and is retained for further investigation; the smaller resolved stack and regression logs are in the same diagnostics directory. The desert test generated and submitted all three desert families at the user's low density, recorded separately in the Parallax developer guide.
